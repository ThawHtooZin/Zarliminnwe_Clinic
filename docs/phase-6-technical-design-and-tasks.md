## Clinic Management System - Phase 6

### Purpose

Phase 6 improves production readiness and clinic operations on top of completed Phases 1–4. It adds administration and access control, fixes POS stock behavior, rebuilds the patient domain into patients + visit records, and improves navigation UX.

Phase 5 (Hardening) remains on hold.

This document is for technical design and Epic breakdown only. No application code is generated by this document.

## 1. Strict Phase 6 Scope

### 1.1 Included

- User management with admin password reset.
- Role management and permission management (screen + route access only).
- Dashboard analytics UI focused on pharmacy-first operations and high-level finance:
  - Actionable stock alerts (low stock, expiring batches, pending stock counts).
  - Daily finance cards (today's service income, today's pharmacy sales, today's expenses).
  - 7-day revenue trend (service income + pharmacy sales).
  - Clinic activity card (today's patient visits).
- Grouped scrollable sidebar navigation.
- Finance reference seeders wired for fresh environments.
- POS add-to-cart stock validation.
- Parent-unit breakdown at POS with model-backed stock allocation on sale lines.
- Patient module: master patients, visit records, stackable diagnoses, visit detail with linked income.
- POS optional link to today's recent patient visit records (latest visit selector).
- Data migration path from Phase 4 `patient_visits` to the new patient model.
- Audit logs for new admin and patient flows.

### 1.2 Explicitly Excluded

- Phase 5 hardening program (deferred).
- Full EHR (vitals, prescriptions as clinical records, lab results, treatment plans, medical notes library).
- Complex EHR dashboard graphs and patient demographic charts.
- Deep accounting charts and advanced financial analytics dashboards.
- Insurance claims and third-party billing.
- Patient portal or telemedicine.
- Doctor scheduling boards and complex intake queue systems.
- Per-feature / per-button permission granularity.
- Multi-branch support.
- Stock ledger changes driven by patient module actions.

### 1.3 Boundary Rules

- Pharmacy sales, stock posting, and unit conversion rules remain in inventory/sales domains.
- Patient module does not post stock movements.
- POS checkout must work with no patient visit selected.
- Pharmacy sales remain stored only in `sales` / `sale_lines` (never copied into `income_entries`).
- Detailed income UIs aggregate `income_entries` and completed `sales` at read time for transparency.
- Finance Summary may continue to show pharmacy sales as a rolled-up total; detailed lists must show line-level pharmacy sales.
- One migration file per database table.
- Dedicated seeder file per seedable model; no category dump inside `DatabaseSeeder.php` beyond `call([...])`.

## 2. Technical Design

### 2.1 Architecture Goals

- Evolve Phase 4 patient data without breaking finance traceability.
- Keep patient master data separate from per-visit clinical/financial records.
- Use patient visit records as the POS patient context source.
- Keep dashboard analytics actionable and lightweight for frontline staff:
  - Emphasize operational alerts and today's financial health.
  - Avoid non-operational visuals that increase cognitive load.
- Reuse `UnitRelationshipService` for POS availability and integer auto-unpack; do not duplicate conversion math in Blade or Alpine.
- Stock balances and POS deductions are **integer-only**. No fractional parent deductions (e.g. 0.5 boxes). When sale-unit stock is insufficient, checkout posts **1 whole parent unit OUT**, **conversion-factor child units IN** (auto-unpack), then **sale-unit OUT** for the sold quantity.
- Represent parent-unit breakdown on sale lines in the database for auditability.
- Replace hard-coded route role groups gradually with permission checks driven by data.
- Keep every Epic shippable and testable in isolation.

### 2.4 Dashboard Metrics Contract (Phase 6)

Dashboard data points:

- `lowStockCount`: Count of products currently below reorder threshold.
- `expiringBatchesCount`: Count of `stock_batches` expiring within 30 days or already expired, with remaining `stock_balances.quantity > 0`.
- `pendingCounts`: Count of `stock_counts` where status is `draft` or `submitted`.
- `todayServiceIncome`: Sum of `income_entries.amount` for today (`received_at` date).
- `todayPharmacySales`: Sum of `sales.grand_total` for completed sales today (`sold_at` date).
- `todayExpenses`: Sum of `expense_entries.amount` for today (`expense_date`).
- `todayPatientVisits`: Count of `patient_visit_records` created today.
- `revenueTrend`: Last 7 days grouped daily combined revenue (`service income + completed pharmacy sales`).

Dashboard visualization rules:

- Keep the dashboard to three sections only:
  - Actionable Alerts.
  - Today's Overview.
  - 7-Day Revenue Trend.
- Do not add complex EHR charts, patient demographic analysis charts, or deep accounting dashboards.
- Use design-system card styling (`bg-white border border-gray-200 rounded-lg shadow-sm`) and primary brand text (`text-[#00535b]`).

#### Patients

Responsibilities:

## 3. Core Data Model

### 3.1 `patients`

Master patient profile.

Key fields:

- `id`
- `patient_code` (unique, auto-generated, human-readable; e.g. `PAT-20260527-0001`)
- `name`
- `age`
- `address`
- `created_by` (nullable FK `users`)
- timestamps

Rules:

- `patient_code` is immutable after create.
- `name`, `age`, and `address` are required on create unless migration rules say otherwise for legacy rows.
- Search by `patient_code` or `name`.

### 3.2 `patient_visit_records`

One row per patient visit (replaces Phase 4 visit-only table concept).

Key fields:

- `id`
- `patient_id` (FK `patients`)
- `visited_at`
- `status` (`open`, `closed`) — default `open`
- `created_by` (FK `users`)
- timestamps

Rules:

- A visit record belongs to exactly one patient.
- Visit datetime is required.
- Closing a visit is allowed without blocking pharmacy sales.

### 3.3 `patient_diagnoses`

Stackable diagnosis entries per visit record.

Key fields:

- `id`
- `patient_visit_record_id` (FK)
- `diagnosis_text`
- `recorded_at`
- `recorded_by` (FK `users`)
- timestamps

Rules:

- Multiple rows per visit record (stacked history).
- Doctors may add diagnoses later; existing rows are not silently overwritten.
- Editing `diagnosis_text` is allowed; changes are audited.

### 3.4 `sales` (alter existing table)

Replace legacy patient link with visit-record context.

Changes:

- Add `patient_visit_record_id` (nullable FK `patient_visit_records`).
- Migrate data from `patient_visit_id` where possible, then drop `patient_visit_id` in a dedicated migration after backfill.

Rules:

- FK remains nullable.
- Completed sale stores selected `patient_visit_record_id` from POS latest-visit selector.
- Receipt and sale detail show patient name/code from the linked visit record.

### 3.5 `sale_line_stock_allocations`

Model-backed parent-unit breakdown and deduction plan per sale line.

Key fields:

- `id`
- `sale_line_id` (FK `sale_lines`)
- `product_unit_id` (FK `product_units` — unit actually deducted from balance)
- `quantity` (in `product_unit_id` unit)
- `is_parent_breakdown` (boolean)
- timestamps

Rules:

- Created at checkout (and held-sale save if allocations are chosen before complete).
- Sum of allocations must match stock posted for that line via `StockPostingService`.
- When `is_parent_breakdown` is true, `product_unit_id` is a parent unit of the sold unit on the sale line.

### 3.6 `roles`

Key fields:

- `id`
- `slug` (unique; e.g. `admin`, `pharmacist`, `cashier`, `stock_manager`)
- `name`
- `description` (nullable)
- `is_system` (boolean — prevent delete of core roles)
- timestamps

### 3.7 `permissions`

Key fields:

- `id`
- `slug` (unique; e.g. `screen.pos`, `route.sales.store`)
- `name`
- `type` (`screen` | `route`)
- `route_name` (nullable — Laravel route name for route permissions)
- `screen_key` (nullable — matches navigation config key)
- timestamps

### 3.8 `role_permission` (pivot)

Key fields:

- `role_id`
- `permission_id`

Unique index on (`role_id`, `permission_id`).

### 3.9 `users` (alter existing table)

Changes:

- Add `role_id` (nullable FK `roles`) while migrating from string `role` column.
- Keep string `role` temporarily for backward compatibility during Epic 2, then remove after migration.

Password reset:

- Use Laravel password reset tokens or admin-set temporary password flow documented in Epic 2.

### 3.10 `income_entries` (alter existing table)

Changes:

- Rename/replace `patient_visit_id` with `patient_visit_record_id` (FK `patient_visit_records`).
- Migrate existing links from legacy visits during patient Epic.

### 3.11 Legacy `patient_visits`

- Do not extend with new features.
- Migrate rows into `patients` + `patient_visit_records` (one patient per legacy row using name+age heuristic or 1:1 mapping — see migration Epic).
- Drop table in final migration after verification.

## 5. POS Design

### 5.1 Product search API (extend `ProductSearchController`)

For each sale unit in JSON payload, include:

- `available_quantity` (in sale unit)
- `can_add_directly` (bool)
- `can_break_from_parent` (bool)
- `parent_unit` object nullable (`id`, `name`, `abbreviation`, `available_in_parent_unit`)

### 5.2 Add-to-cart rules

| Condition | POS behavior |
|-----------|----------------|
| Enough stock in sale unit | Normal unit button adds line |
| No sale-unit stock, parent can cover | Unit remains addable; checkout auto-unpacks whole parent units (no UI toggle) |
| Insufficient total | Block add; show clear message |
| Same `productId` + `unitId` added again | Increment existing cart line quantity (no duplicate row) |

### 5.2.1 Integer stock and auto-unpack (checkout)

- `stock_balances.quantity` and stock movements for POS must remain **whole numbers** per `product_unit_id`.
- **Outlawed:** fractional cross-unit deduction (e.g. deducting `0.05` boxes when selling pills).
- **Required:** when direct sale-unit stock is insufficient, checkout always loops: deduct integer sale-unit stock when available; otherwise **unpack exactly 1 parent unit** (`unit_unpack_out` on parent, `unit_unpack_in` on child using the unit's whole-number `conversion_factor`), then continue until the sale quantity is fulfilled.
- Availability `max_qty` = sum of integer direct sale-unit stock plus integer-convertible ancestor stock (e.g. 1 box + 2 strips → sellable pills = `100 + 20` when factors are 10×10).
- Sale line quantity must be a **positive whole number**.

### 5.3 Cart line shape (Alpine)

Extend cart line JSON:

```json
{
  "productId": 1,
  "unitId": 3,
  "quantity": 1,
  "quantity": 1
}
```

### 5.4 Patient section (latest visit selector)

- Load `GET /sales/patient-visits/today-recent` (new endpoint).
- Dropdown shows today's recent patient visits (latest first) with patient code + name + visit time.
- **Active queue only:** exclude any `patient_visit_record` that already has a `sales` row with `status = completed` (prevents double-billing the same visit at POS).
- Select visit → set `patientVisitRecordId` hidden input on checkout/hold forms.
- No temporary intake records, no separate intake queue source, and no patient creation from POS.

## 7. Data Migration Strategy (Phase 4 → Phase 6)

### 7.1 `patient_visits` → patients + visit records

For each legacy `patient_visits` row:

1. Create `patients` with `name` = `patient_name`, `age`, `address` = empty string or `'-'` if unknown.
2. Generate `patient_code`.
3. Create `patient_visit_records` with same `visited_at` and `created_by`.
4. Store mapping `old_visit_id → new_visit_record_id` for FK updates.

### 7.2 `income_entries.patient_visit_id`

- Update to `patient_visit_record_id` using mapping table.

### 7.3 `sales.patient_visit_id`

- Update to `patient_visit_record_id` where set.

### 7.4 Routes and controllers

- Standalone `patient-visits` list/create/store/edit/update routes are removed.
- Visit creation uses `patients/{patient}/visit-records/create` only.
- Visit detail/diagnosis routes remain at `patient-visits/{patientVisit}` for deep links from patient profile and POS.

## 10. Key Risks And Decisions

### Risk: Patient module grows into full EHR

**Decision:** Allow only diagnosis stacking on visit records plus existing finance links. Reject vitals, prescriptions, labs, and non-linear intake flows in validation tests.

### Risk: POS blocks sales incorrectly

**Decision:** Availability logic must match `calculateIntegerSaleFulfillment` rules; add feature tests for direct sale unit, integer auto-unpack, cart line aggregation, and blocked insufficient stock.

### Risk: Breaking Phase 4 finance reports

**Decision:** Migrate `income_entries` FK in same release as visit records; update report queries and tests in same Epic.

### Risk: Permission system too large for Phase 6

**Decision:** Screen + route only; default seed maps to current `role:*` middleware behavior; optional dual-run (middleware + permission) during Epic 2.

### Risk: Legacy `patient_visits` references left in code

**Decision:** Single migration Epic with grep checklist; remove `PatientVisit` model after cutover.

## 11. Finance & POS UI Unification (Planned Delta)

### 11.1 Problem

Today, completed POS sales live only in `sales`. They appear as a lump sum in Finance Summary (`FinanceSummaryService::sumPharmacySales`) but not as line items on:

- Patient Visit detail (`patient-visits.show`)
- Finance Income list (`finance.income.index`)
- Income Report (`reports.finance-income`)

Staff cannot see full visit-level or date-range income transparency without opening Sales History separately.

### 11.2 Design Principles

| Rule | Detail |
|------|--------|
| **No data duplication** | Never insert POS rows into `income_entries`. Void/stock reversal stays on `sales`. |
| **Read-time aggregation** | Domain services query both tables, normalize to a shared view DTO, merge, sort, paginate. |
| **Pseudo-category** | Pharmacy sales display category label `Pharmacy Sale` (UI constant; not an `income_categories` row). |
| **Status filter** | Only `sales.status = completed` appear as income. Voided sales are excluded. |
| **Visit linkage** | Only sales with `patient_visit_record_id` appear on visit detail. Unlinked walk-out sales stay off visit detail but may appear on finance income lists. |

### 11.3 Unified Income Row Contract

Introduce a read-only value object (not an Eloquent model), e.g. `App\Domain\Finance\Data\UnifiedIncomeLine`:

| Field | Income entry source | Pharmacy sale source |
|-------|---------------------|----------------------|
| `source` | `income_entry` | `pharmacy_sale` |
| `source_id` | `income_entries.id` | `sales.id` |
| `occurred_at` | `received_at` | `sold_at` |
| `category_label` | `incomeCategory.name` | `Pharmacy Sale` |
| `amount` | `amount` | `grand_total` |
| `payment_method` | `payment_method` | `payment_method` |
| `patient_visit_record_id` | FK (nullable) | FK (nullable) |
| `patient_display` | patient code + name via visit | patient code + name via visit |
| `recorded_by` | `receivedBy.name` | `cashier.name` |
| `description` | `description` | `sale_number` (or receipt summary) |

### 11.4 New / Extended Domain Services

#### `App\Domain\Finance\Services\UnifiedIncomeQueryService` (new)

Responsibilities:

- `paginatedForFilters(array $filters): LengthAwarePaginator` — merged list for finance screens.
- `forPatientVisit(PatientVisitRecord $visit): Collection` — all lines for one visit (no pagination).
- `visitIncomeTotal(PatientVisitRecord $visit): float` — optional helper for subtotals.

Implementation notes:

- Build two Eloquent queries with identical filter semantics where possible.
- Map each result set to `UnifiedIncomeLine`.
- Merge collections, sort by `occurred_at` desc then `source_id` desc.
- Paginate in PHP for page 1..N (acceptable for clinic scale) **or** use SQL `UNION ALL` subquery for DB-level pagination (preferred for report screen).
- Apply filters:
  - Date range → `received_at` / `sold_at`
  - Payment method → both tables
  - Patient visit → both tables on `patient_visit_record_id`
  - Received by / cashier → `received_by` / `sold_by`
  - Category → income entries by `income_category_id`; pharmacy sales included when filter empty or when explicit pseudo-filter `pharmacy_sale` selected

#### `App\Domain\Finance\Services\FinanceReportService` (extend)

- Delegate `incomeReport()` to `UnifiedIncomeQueryService` instead of `IncomeEntry` only.
- Keep `expenseReport()` unchanged.

#### `App\Domain\Patients\Services\PatientVisitRecordService` (extend, optional)

- Optional thin wrapper `incomeLinesForVisit()` calling `UnifiedIncomeQueryService::forPatientVisit()` to keep controller slim.
